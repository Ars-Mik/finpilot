# Архитектура FinPilot

FinPilot состоит из React-клиента, Express API и PostgreSQL. Клиент работает через REST API, сервер хранит финансовые записи и выполняет расчёты. Демо-режим предназначен только для тестовых данных.

## Компоненты

- `client/src/pages/` — экраны обзора, операций, счетов, бюджетов, регулярных правил, прогноза и аналитики.
- `client/src/api/` — HTTP-запросы, обработка сессии и ошибок.
- `server/src/app.ts` — маршруты API и проверка входных данных через Zod.
- `server/src/modules/` — репозитории PostgreSQL, модели и бизнес-расчёты.
- `server/src/security/` — гостевые сессии и контекст рабочего пространства.
- `server/migrations/` — последовательные SQL-миграции.

Денежные суммы передаются в целых копейках. Переводы между своими счетами записываются как одна операция; остатки рассчитываются по исходному остатку, доходам, расходам и переводам.

## Основные маршруты

| Группа | API | Назначение |
| --- | --- | --- |
| Сессия | `GET /api/session`, `POST /api/demo/reset` | Создание гостя, CSRF, сброс демоданных |
| Операции | `/api/transactions`, `/api/transactions/overview` | Учёт, поиск, фильтры и сводка |
| Счета | `/api/accounts`, `/api/transfers` | Счета и переводы |
| Бюджеты | `/api/budgets` | Лимиты по месяцам и категориям |
| Регулярные | `/api/recurring`, `POST /api/recurring/apply` | Правила и ручное применение начислений |
| Цели | `/api/goals`, `/api/goals/:id/allocations` | Цели, резервирование и история |
| Прогноз | `POST /api/forecast/simulate` | Денежный поток и виртуальные составные сценарии |
| Аналитика | `GET /api/analytics` | Расходы, счета, периоды |
| Состояние | `GET /api/health` | Проверка процесса API |

## Данные и изоляция

Финансовые таблицы: `accounts`, `transactions`, `account_transfers`, `monthly_budgets`, `recurring_rules`. Каждая запись относится к `workspace_id`. Сессионные таблицы и метаданные рабочих пространств хранятся отдельно.

Для финансовых таблиц включены PostgreSQL Row-Level Security и `FORCE ROW LEVEL SECURITY`. API использует непривилегированную роль `finpilot_app`. Контекст workspace задаётся сервером внутри транзакции, чтобы подключения из пула не переносили его между гостями. Ссылки между финансовыми записями дополнительно ограничены составными внешними ключами с workspace ID.

При первом визите создаются случайный токен сессии, workspace и набор демонстрационных данных. Токен хранится у пользователя в HttpOnly cookie, а в БД — его хеш. Изменяющие запросы требуют CSRF-токен. Сброс затрагивает только workspace текущего гостя. Лимит создания сессий хранится в PostgreSQL и действует между экземплярами API.

Административный `DATABASE_URL` используется только для миграций и обслуживания. API получает только `APP_DATABASE_URL`. Публичный доступ к PostgreSQL не допускается.

## Прогноз и регулярные операции

Прогноз опирается на текущие остатки, будущие операции и повторяющиеся правила. API по-прежнему принимает старый формат разовой покупки. Новый формат `scenario: { kind: "plan", title, changes }` допускает 1–5 виртуальных изменений, каждое с типом `income`, `expense` или `saving`, частотой `once` либо `monthly`, суммой и датой начала. Месячные события используют календарный день начала (31-е число переносится на последний день короткого месяца). Экономия увеличивает виртуальный будущий остаток, но не изменяет реальные расходы или правила. Все изменения применяются только к линии сценария; базовая линия, статистика реальных событий и PostgreSQL не изменяются. Сценарий существует только в текущем интерфейсе, без серверного или браузерного сохранения.

Регулярные правила поддерживают недельный и месячный шаг. Повторяющиеся операции применяются через `POST /api/recurring/apply`; для автоматического начисления предусмотрена команда `recurring:apply`, запускаемая внешним расписанием. Повторное применение защищено уникальностью сочетания правила и даты.

## Известные ограничения

- Есть изолированная гостевая демоверсия, но нет пользовательских аккаунтов и восстановления доступа.
- Категории фиксированы; нет пользовательских категорий.
- Можно сравнить базовый прогноз с одним составным виртуальным сценарием. Сохранения нескольких отдельных сценариев, их версий и привязки к целям пока нет.
- Отсутствуют импорт и экспорт транзакций, уведомления.
- Публичная инфраструктура, backup/restore и мониторинг требуют отдельной проверки перед релизом.


### Резервирование средств для целей

Таблицы `savings_goals` и `goal_allocations` изолированы по `workspace_id` через PostgreSQL RLS и составные внешние ключи. Запись в `goal_allocations` показывает резервирование (`+`) или освобождение (`-`) средств, **но не движение денег**: она не меняет баланс счёта или статистику расходов. При добавлении резерва проверяются текущий баланс счёта и сумма уже зарезервированных средств. Транзакция блокирует строку счёта, предотвращая конкурирующие резервирования сверх доступной суммы. Обычные платежи могут позднее уменьшить фактический остаток ниже суммы резервов — интерфейс должен показывать эту разницу, не обещая банковской блокировки средств. Архивирование цели освобождает зарезервированное; история резервирований сохраняется до сброса или очистки гостевого пространства.
