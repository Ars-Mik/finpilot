# FinPilot — этап 10: финансовый прогноз

## Что добавлено

Страница `/forecast` сравнивает два результата:

1. **Базовый прогноз** — текущий остаток всех счетов + будущие операции из БД + будущие начисления активных расписаний.
2. **Что, если?** — базовый прогноз за вычетом одной виртуальной покупки в выбранную дату.

Горизонт: 3, 6 или 12 календарных месяцев, **включая текущий**. Границы интервала определяются на backend в UTC. Прогноз показывает остаток на конец каждого месяца, минимальный остаток в течение периода и первую дату его ухода ниже нуля.

## Структура

- `server/src/modules/forecast/forecast.schema.ts` — строгая Zod-схема запроса и типы.
- `server/src/modules/forecast/forecast.repository.ts` — интерфейс источника данных.
- `server/src/modules/forecast/pg-forecast.repository.ts` — чтение согласованного снимка PostgreSQL (`REPEATABLE READ READ ONLY`).
- `server/src/modules/forecast/forecast.service.ts` — чистые расчёты, без SQL и HTTP.
- `server/tests/forecast.test.ts` — проверка логики и API.
- `client/src/api/forecast.ts` — HTTP-клиент.
- `client/src/pages/ForecastPage.tsx` — сценарий, график и помесячная таблица.

**Миграций и дополнительных npm-зависимостей нет.** Existing records and tables are unchanged.

## API

`POST /api/forecast/simulate`

Без покупки:

```json
{ "months": 6, "scenario": null }
```

С покупкой:

```json
{
  "months": 6,
  "scenario": {
    "title": "Ноутбук",
    "amountCents": 9000000,
    "date": "2026-11-15"
  }
}
```

Значение `months` — только `3`, `6` или `12`; сумма задаётся **в копейках** и не должна превышать 10 млрд ₽; дата покупки — строго позже сегодняшней даты сервера и не позже конца горизонта. Никакая операция не записывается в PostgreSQL при симуляции.

Ответ содержит `data.currentBalanceCents`, `data.plannedEvents`, `data.months`, `data.baseline`, `data.withScenario`, `data.asOf`, `data.through`, `data.scenario`.

## Правила финансового расчёта

- Базовый остаток — сумма начальных остатков счетов + чистый поток **фактических операций с датами по сегодняшний день включительно**.
- Ручные транзакции с датами в будущем включаются в будущий поток, а не в базовый остаток.
- Активные еженедельные и ежемесячные правила учитываются **только на будущие даты**. Правила на паузе не используются.
- Если будущая операция уже привязана к правилу и дате начисления, повторное будущее начисление не создаётся в расчёте.
- Переводы между собственными счетами не учитываются, поскольку суммарные деньги от них не меняются.
- Деньги считаются в целых копейках, операции проверяют безопасный целочисленный диапазон JavaScript.
- В один день несколько событий агрегируются до **остатка на конец дня**. Внутридневной порядок не моделируется.
- Симуляция покупки не меняет реальные данные и не создаёт транзакций.

### Ограничения первой версии

- Прогноз не оценивает незапланированные расходы, проценты по депозитам, инфляцию и неопределённость будущих доходов.
- Исторические просроченные начисления, ещё не записанные в операции, автоматически не учитываются в стартовом остатке. Их можно записать на странице «Регулярные».
- Прогноз строится для **суммы всех счетов**, без учёта возможного отрицательного остатка на отдельном счёте.
- Нет авторизации и изоляции данных разных пользователей — API нельзя выставлять в публичный интернет.

## Сценарии ручной проверки

1. Проверить прогноз на 3, 6 и 12 месяцев и верность текущего баланса.
2. Создать регулярную будущую зарплату или аренду — обновить прогноз и увидеть изменение соответствующего месяца.
3. Выбрать дату покупки внутри периода — при применении должен уменьшиться только сценарный остаток.
4. Нажать «Без покупки»: обе линии снова совпадают, **данные базы не изменяются**.
5. Рассчитать сценарий с суммой выше ожидаемого остатка: дата первой нехватки денег появляется.
6. Пауза у регулярного правила убирает его будущие начисления из прогноза.
7. Проверить F5 и работу при отключённом API: приложение показывает ошибку, не создаёт операции.
8. Посмотреть мобильный экран, таблицу со скроллом, доступность подписей и кнопок.
