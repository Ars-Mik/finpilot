# FinPilot

**FinPilot** — fullstack-приложение для учёта личных финансов, анализа расходов и прогнозирования денежного потока. Проект развивается как портфолио Fullstack JavaScript / TypeScript разработчика.

> **Статус: MVP / гостевая демоверсия.** Основные модули реализованы, но публичный production-релиз ещё не завершён. Не используйте сервис для реальных финансовых данных.

## Возможности

- **Обзор:** сводные показатели финансов и недавние операции.
- **Операции:** доходы и расходы, добавление, редактирование, удаление, поиск, фильтры и пагинация.
- **Счета:** учёт остатков и переводы между своими счетами.
- **Бюджеты:** месячные лимиты по категориям, фактические расходы и контроль превышений.
- **Цели:** сумма и срок накопления, резервирование внутри счёта, история пополнений, прогресс и архив.
- **Регулярные операции:** правила повторяющихся доходов и расходов, ручное применение и отдельная задача для автоматических начислений.
- **Прогноз:** будущий денежный поток и сравнение с виртуальным сценарием до пяти разовых или ежемесячных изменений доходов, расходов и экономии.
- **Аналитика:** распределение расходов по категориям, динамика по месяцам и анализ по счетам.
- **Интерфейс:** адаптивная React UI, светлая и тёмная темы; базовые проверки доступности.
- **Гостевая демоверсия:** демоданные, изолированные рабочие пространства и сброс только своей сессии.

## Технологии

| Слой | Инструменты |

## Локальный запуск (Windows PowerShell)

Требуются **Node.js 22.12+**, npm, Docker Desktop с работающим Docker Engine и Git.

Запустите PostgreSQL из **корня репозитория**:

```powershell
docker compose up -d postgres
```

Первый запуск backend (не перезаписывайте существующий `server/.env`, если БД уже настроена):

```powershell
cd server
Copy-Item .env.example .env     # только если .env ещё не существует
npm ci
npm run db:migrate
npm run dev
```

Если обновляете существующую базу, **до миграций** сделайте резервную копию и проверьте восстановление на отдельной базе. Эксплуатационные требования описаны в [DEPLOY.md](DEPLOY.md).

Backend: `http://127.0.0.1:3001`; проверка работоспособности: `http://127.0.0.1:3001/api/health`.

В другом терминале (из корня репозитория):

```powershell
cd client
npm ci
npm run dev
```

Откройте `http://localhost:5173`. Vite перенаправляет запросы `/api` на локальный backend.

При первом обращении к `GET /api/session` сервер создаёт гостевую сессию и заполняет её демонстрационными данными. Для работы с API используются сессионная cookie и CSRF-токен.

## Проверки

Backend:

```powershell
cd server
npm run build
npm test
npm audit --omit=dev
```

Frontend:

```powershell
cd client
npm run build
npm run lint
npx playwright install chromium
npx playwright test
```

**Интеграционные тесты RLS** запускаются только при заданной переменной `INTEGRATION_DATABASE_URL`; без неё соответствующий тест пропускается. Используйте отдельную тестовую БД с применёнными миграциями и непривилегированным пользователем `finpilot_app`. Workflow GitHub Actions поднимает для них изолированный PostgreSQL.

Для независимой проверки RLS и гостевых сессий используйте `scripts/Test-GuestIsolation.ps1`: он запускает отдельную PostgreSQL через `docker-compose.qa.yml`.

## Автоматические начисления

Команда `npm run recurring:apply` в каталоге `server` обрабатывает только действующие гостевые пространства. Для неё нужен `APP_DATABASE_URL` с ограниченными правами; `DATABASE_URL` администратора ей не нужен. Запускайте команду отдельной периодической задачей (например, каждые 15 минут), а не внутри HTTP API. Повторный запуск не создаёт дубли благодаря уникальному индексу в PostgreSQL.

Обработка дат ведётся по UTC. Существующая логика регулярных правил охватывает прошедший год; более старые начисления автоматически не восстанавливаются. В локальной среде сначала проверяйте задачу на изолированной QA-базе.

## Безопасность и ограничения

- Гостевая сессия хранится в HttpOnly cookie; в PostgreSQL сохраняется только хеш токена.
- У запросов на изменение данных есть проверка CSRF; доступ между рабочими пространствами ограничен PostgreSQL RLS.
- Runtime-сервер подключается под отдельной ограниченной ролью `finpilot_app`; учётную запись администратора PostgreSQL используют только миграции и обслуживание.
- Исторические данные из базы при миграции 005 переносятся в workspace типа `legacy` и не доступны гостевому интерфейсу.
- Отсутствуют полноценные личные аккаунты и процедуры для безопасного приёма реальных финансовых данных.
- Лимит создания новых гостевых сессий общий для всех экземпляров API и хранится в PostgreSQL. Он не заменяет защиту от массовых HTTP-запросов на reverse proxy.

**Не публикуйте** `.env`, реальные финансовые данные, приватные дампы БД и учётные данные. Пример `.env.example` содержит исключительно локальные учебные значения.

### Финансовые цели

Раздел **Цели** и `/api/goals` позволяют создавать и редактировать цели, резервировать средства на выбранном счёте, видеть историю, прогресс и ориентировочный ежемесячный взнос, возвращать резерв и архивировать цель. Сумма резервирования не учитывается как расход или перевод. Свободный остаток равен балансу счёта за вычетом резервов всех его активных целей. Если обычные платежи уменьшили этот остаток ниже нуля, интерфейс сообщает о дефиците: резервирование не является банковской блокировкой денег.

### Сохранённые сценарии (API)

Гостевая сессия может хранить до 10 планов. `GET /api/forecast/scenarios` возвращает список, `POST` создаёт сценарий, а `GET`, `PUT` и `DELETE /api/forecast/scenarios/:id` позволяют открыть, заменить или удалить его. При создании и замене используется тот же формат, что и при расчёте: `{ "months": 3, "scenario": { "kind": "plan", "title": "Пример", "changes": [ ... ] } }`. Даты должны быть будущими и попадать в выбранный период. Сохранённый сценарий остаётся доступным, когда дата проходит, но для нового расчёта её нужно обновить. Виртуальные изменения не создают реальные операции и не резервируют деньги.
