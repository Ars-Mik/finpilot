# Развёртывание FinPilot

Этот документ — список условий перед публичным запуском. Он не заменяет конфигурацию выбранного хостинга.

## Сеть

- Выдать frontend и API один HTTPS-origin. Проксировать `/api/*` на Node.js, остальные пути — на frontend.
- Весь HTTP перенаправлять на HTTPS. Убедиться, что браузер получает `Secure`, `HttpOnly`, `SameSite=Lax` cookie с префиксом `__Host-` и `Path=/`.
- Не открывать порт Node.js и PostgreSQL в публичный интернет. Разрешать API входящие соединения только от доверенного proxy.
- Установить `TRUSTED_PROXY_CIDRS` в точные адреса или CIDR proxy. Для proxy на том же хосте допустим `loopback`; `direct` — только без proxy. Не доверять всем `X-Forwarded-*` заголовкам.
- На proxy отдельно ограничить частоту всех HTTP-запросов, одновременные подключения, размеры запросов и время ожидания. Лимит 10 новых гостевых сессий на IP в PostgreSQL не заменяет эту защиту.

## Конфигурация

- Использовать `server/.env.production.example` только как шаблон. Не сохранять рабочий `.env` в Git, логах, сборках или публичных артефактах.
- Для API предоставить `APP_DATABASE_URL`, но **не** `DATABASE_URL` с правами владельца базы.
- Для миграций и очистки использовать отдельную задачу с `DATABASE_URL` и `APP_DATABASE_URL`. Не запускать миграции при каждом старте API.
- Настроить `NODE_ENV=production`, `CLIENT_ORIGIN` с `https://`, случайный `SESSION_SECRET` длиной 32 байта (64 hex-символа), явный `TRUSTED_PROXY_CIDRS`.
- Не использовать пароли из локального `docker-compose.yml` на публичном сервере. Базу разместить в приватной сети и настроить TLS для соединения с ней в соответствии с инфраструктурой.
- Для контейнера с отдельным reverse proxy назначить `HOST` по сетевой топологии. `127.0.0.1` подходит только когда proxy соединяется по loopback.

## Обслуживание

- Запускать `npm run recurring:apply` каждые 15 минут в отдельной задаче с **только** `APP_DATABASE_URL`. Не выдавать этому процессу административный `DATABASE_URL`. Задача одноразовая: очередной запуск выполняет планировщик (cron, systemd timer или задача платформы). Встроенная блокировка PostgreSQL не допускает пересечения двух запусков. Ненулевой код завершения означает, что были ошибки обработки и необходима проверка логов.
- Начисления рассчитываются в UTC, только для действующих гостевых сессий. Восстановление пропущенных дат ограничено прошедшим годом; для более ранних начислений нужна отдельная процедура.
- Запускать `npm run db:cleanup-guests` отдельной административной задачей не реже одного раза в час; отслеживать ошибки и число удалённых пространств.
- Хранить резервные копии PostgreSQL отдельно от рабочего сервера, с проверяемым сроком хранения и ограниченным доступом.
- Прежде чем считать резервирование рабочим, восстановить дамп в **отдельную** временную БД и проверить целостность данных. `pg_restore -l` проверяет читаемость каталога архива, но не само восстановление.
- Контролировать HTTP 5xx, частоту 429, ошибки базы, нагрузку, количество активных гостевых сессий и срок действия TLS-сертификата. Не писать сессионные cookie, CSRF-токены, секреты и полный URL базы в логи.
- При обновлении запускать `npm ci`, миграции с отдельными правами, затем обычное приложение. Проверять возможность отката кода без повторного применения SQL-миграций.

## Проверка перед публикацией

1. GitHub Actions зелёный; отдельная PostgreSQL QA проходит RLS-тесты.
2. На HTTPS-домене `GET /api/health` возвращает 200.
3. В двух приватных окнах создаются разные гости, данные не пересекаются; повторное открытие страницы сохраняет сессию, сброс затрагивает только своего гостя.
4. `/api/*` возвращает `Cache-Control: no-store`; чувствительные ответы не кэшируются на proxy.
5. Cookie имеет необходимые атрибуты, CSRF защищает изменение данных, посторонний Origin отклоняется.
6. Планировщик начислений, фоновая очистка и восстановление резервной копии проверены на тестовой базе.
7. Проверены мобильная версия, 404/500 и поведение при временной недоступности базы.

До завершения всех проверок не публиковать приложение как готовый сервис для хранения реальных финансовых данных.
